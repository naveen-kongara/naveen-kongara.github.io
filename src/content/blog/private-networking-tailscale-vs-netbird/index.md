---
title: "Evaluating two mesh VPN tools for private connectivity between two cloud providers"
description: "We needed a private network path between AWS and a bare-metal provider. We tested two self-hosted mesh VPN options before picking one and later migrating it to a different provider."
date: "Feb 16 2026"
---

We run some workloads on AWS and some on a bare-metal cloud provider, and needed a private network path between the two — no public internet hop for internal traffic between environments. Rather than set up a traditional site-to-site VPN with a gateway in each VPC, we evaluated two self-hosted mesh VPN tools that build a peer-to-peer overlay network instead: one built on Headscale (a self-hosted control plane compatible with Tailscale's client), and one called Netbird.

**First test: the Tailscale-compatible option.** We stood up the control plane and connected nodes in both environments. It worked — we could reach private addresses across providers through the mesh — and we measured roughly 50 Mbps download, 30 Mbps upload, and about 250ms latency between a node on AWS and one on the bare-metal side. The latency is mostly a function of physical distance between the two regions we were testing, not the tool. The real limitation we found was architectural: this setup wants a gateway node in every VPC/subnet plus an overall control plane node, which is more infrastructure to run and keep patched than we wanted for what was, at its core, a routing problem between two environments.

**Second test: Netbird.** Conceptually similar — a control plane plus WireGuard-based peer connections — but with a detail that mattered for our case: it establishes direct peer-to-peer connections when possible and automatically falls back to a relay server when a node is behind NAT or otherwise unreachable directly. We tested both paths. A node with a public address connected peer-to-peer directly to the bare-metal side. A node on a private address, with no inbound path, fell back to a relay and still connected successfully, just through a different path. We also tested route-based access: installing the client on one internal instance and using it as a routing peer so that other instances (that don't have the client installed at all) could reach a different internal network through it. That worked too — we could SSH to a private-network instance from the bare-metal side purely over the mesh, with a single routing peer handling traffic for a whole address range instead of installing the client everywhere.

The automatic peer-to-peer/relay fallback was the deciding factor over the Headscale-based option. It meant we didn't have to manually design and maintain gateway placement in every network — the tool handled finding the best path itself, and degraded gracefully when a direct path wasn't available instead of just failing.

**Later: moving the control plane.** Some months after rolling this out on the original bare-metal provider, we migrated the whole Netbird setup — control plane and all — to a different bare-metal provider, mainly for cost and account-management reasons unrelated to the tool itself. The migration plan was reviewed, executed, and tested like any other infrastructure move: stand up the new control plane, re-point clients, verify connectivity across all the routes that depended on it, then decommission the old one. Nothing about the earlier evaluation needed to be redone — the tool's behavior under provider migration was exactly what we'd expect from a config-driven mesh network: redeploy the control plane, re-register peers, done.

The broader takeaway: when evaluating mesh VPN tools, don't just test whether two nodes can reach each other under ideal conditions. Test what happens when one side is behind NAT and has no direct path — that's the scenario that actually separates these tools in practice, not raw throughput numbers which tend to be similar across WireGuard-based options anyway.
